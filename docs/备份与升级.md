# 备份与升级

本文适用于 App 2.12.0、服务端和网页后台 2.9.2。相册能恢复，需要同时保留照片原文件、相册数据库和存储密钥。只备份安装包不够。

请备份：

1. 整个服务端数据目录。里面包含所有宝宝的资料、家人及其访问权限、共享照片关系、留言、成长记录和故事册，以及头像、本地上传、生成的预览和加密存储配置所需的密钥文件。
2. 单独挂载的原始图库、本地或 NAS 存储目录，以及对象存储桶中的原文件。
3. 部署配置和存储账号的恢复资料，保存在只有自己能访问的位置。
4. 如果自己构建安卓安装包，保存 `.private` 中的应用签名和签名密码，以便以后安装更新。

数据目录里的 `storage.key` 用来解开数据库中的云存储密钥，必须和数据库配对保存。若部署时改用 `ALBUM_STORAGE_KEY` 提供主密钥，应在自己的密码管理工具中另行备份该值。

## 在网页后台备份

只有家庭管理员可以管理备份。备份始终覆盖全家庭所有宝宝，包括已归档宝宝；切换页面选择的宝宝不会缩小备份范围。

进入“存储与备份”，可以立即创建备份，也可以设置每天或每周自动备份。计划时间使用北京时间，服务需要保持运行，网页无需一直打开。

| 备份内容 | 包含什么 | 恢复时还需要什么 |
| --- | --- | --- |
| 相册资料与全部原文件 | 所有宝宝的相册数据库、家人权限、共享关系、成长记录和故事册、存储密钥、已有头像，以及数据库记录的全部照片和视频原件，包括回收站内容 | 独立副本有自己的原件；仍需按副本启用说明配置服务 |
| 仅相册资料 | 所有宝宝的相册数据库、存储密钥和已有头像，保留家人及访问权限、共享关系、拍摄时间、说明、收藏、留言、成长选择与故事册等资料 | 原照片和视频不在备份中，必须接回原图库、本地或 NAS 目录、对象存储 |

同一张合照关联多个宝宝时，备份保存一份原件和各宝宝的收录关系。各宝宝的照片数相加可能大于原件总数，这是正常情况。

备份取创建时的相册资料，并逐份核对原文件；之后新上传的内容要等下一份备份。无法读取原文件或服务器空间不足时，任务会显示未完成，不能把这份任务当作可用备份。

备份当前只保存在服务器数据目录下的 `backups` 文件夹，即 `ALBUM_DATA/backups`；Docker 中为 `/data/backups`。选择 NAS、OSS、COS 或 S3 保存照片，不会自动把备份也存到那里。完成后在“备份记录”点击“核对备份”，再下载到另一台设备或另行保存到异地。

保留数量可设为最近 1～90 份，默认 7 份。每次成功备份后，会清理超过数量的较早已完成备份；手动与定时备份共用这个数量，不按备份类型分别保留。希望长期保存的那一份，应先下载另存。

备份包含家庭资料及恢复云存储配置所需的密钥，压缩包没有另外加密。请放在只有自己能访问的位置；不要发到公开链接或源码仓库。已经开始但被服务中断的备份会显示失败，需要重新创建；仍在等待的备份可以继续处理。

## 恢复为独立副本

1. 在“存储与备份 → 备份记录”找到已完成的备份，选择“恢复副本”。
2. 核对备份时间、照片、视频和家人数量，确认它是完整备份还是仅相册资料。
3. 输入当前管理员密码后开始恢复。服务会先检查备份，再把内容写到数据目录下的 `restored` 文件夹。
4. 完成后查看页面给出的副本目录及其中的“启用副本说明.txt”。当前相册没有被覆盖，也没有自动切换。
5. 部署者在独立端口或备用服务启用副本，核对无误后再安排切换。

同一台机器上，可以按生成的说明，将另一个服务的 `ALBUM_DATA` 指向副本的 `data` 目录。完整恢复的照片和视频会放在副本本地的 `data/uploads`，`ALBUM_LIBRARY` 可指向副本的 `library` 目录，不再依赖原来的云存储。

副本中的本地存放位置记录了恢复时的绝对目录。若把副本搬到另一台机器，或在 Docker 中改成不同的目录映射，部署者还需调整副本的本地存放路径；仅更改 `ALBUM_DATA` 不会自动改写已保存的存储位置。当前后台没有上传外部备份压缩包并自动迁移路径的入口。

仅资料恢复保留原存储配置，必须继续接上原文件：原图库按说明配置，本地或 NAS 目录仍需允许服务访问，原来保存在旧数据目录中的上传文件需另行复制，云存储仍需能够连接。

副本保留备份时的账号、所有宝宝及其家人访问权限、共享照片关系、各宝宝的回收站、留言和故事册，以及拍摄时间。副本中的旧登录会失效，需要使用备份中的账号密码重新登录。导入任务、备份任务和运行记录不会在副本继续执行，自动备份需要重新设置。当前相册的登录和任务不受影响。

## 直接备份部署目录

最容易核对的方法是暂停上传和相册服务，再复制数据目录和所有本地原文件。运行中的 SQLite 数据库不要只复制一个文件；可以使用 SQLite 在线备份功能，或停服务后复制整个数据目录。

对象存储可启用版本保留或单独备份任务。回收站方便撤销当前宝宝的误移除，归档方便暂时收起宝宝相册；二者都不能代替独立备份。不要把唯一备份放在同一块硬盘上。

## 升级

安卓 App 与服务端可以分别更新。仅更新 App 时，用相同签名的安装包覆盖安装即可保留手机资料；更新服务端或网页后台时，按下面的完整步骤保留数据和配置。

如果服务端仍早于 2.9.2，则应先按下方完整步骤升级，才能使用六位邀请码、简洁邀请、权限开关和按宝宝修改关系。已有账号、权限和登录继续使用，不重置原称呼或角色，也不用重新发出仍然有效的旧邀请。历史上传者继续保留在折叠入口，原记录不删除。完整备份与仅资料备份都会保留按宝宝设置的关系。旧版 App 没有宝宝选择信息时，只能使用服务端默认的可访问宝宝，不能完整使用多宝宝功能。

从已有独立账号的版本升级时，用户名、密码、家人身份和现有登录会话保持不变，不会被重置为 `admin/admin`，也不会因为升级而要求已有账号重新设置密码。默认账号只在建立全新相册时生成一次；完成首次改密后，重启服务不会恢复初始密码。不要为了使用新版而删除或更换已有数据目录。

2.9.2 新生成的邀请码改为六位数字，旧邀请按原来的有效期继续使用。请一起更新服务端和手机，旧版手机可能无法从完整邀请中识别短码。原账号、已加入的家人及访问权限不受影响。邀请码尝试记录会随数据库保留，重启服务不会清空短时间内的尝试限制。

首次从多宝宝功能之前的服务端升级时，旧资料会一次性归到原来的宝宝，包括照片、回收站、家人、留言、动态、成长代表照和故事册。旧邀请只授予原宝宝的权限，不会自动授权新宝宝。更新完整服务的步骤如下：

1. 按上面的清单完成备份，暂停上传和相册服务。
2. 替换程序代码，保留现有数据目录、原始图库、存储密钥和部署配置。不要用空数据目录覆盖现有相册，也不要删除原来挂载的数据卷。
3. 更新依赖并启动新版服务端。使用 Docker Compose 时，在原部署目录运行 `docker compose up -d --build`，沿用原有的数据目录挂载。
4. 在原服务地址下的 `/admin/` 用原家庭管理员账号登录，核对原宝宝的资料和存储位置。Docker 直接沿用原服务和端口提供网页。
5. 用原签名构建的 2.12.0 App 覆盖安装，不必先卸载旧应用。提醒家人一起更新，再按需要新增宝宝及安排访问范围。
6. 抽查旧照片、视频、家人权限和宝宝切换，检查拍摄时间、原文件下载、视频播放、成长与故事册。在测试相册小批量导入，核对重复处理与任务结果；完整备份并在独立副本中验证恢复。

需要修改登录用户名时，进入“我的 → 账号与安全 → 修改用户名”，输入新用户名和当前密码。照片归属、收藏和留言继续属于原来的家人；这台设备继续登录，其他设备需要重新登录。已有用户名无需为了升级而修改。

升级不会自动移动历史照片或改变它们的存储位置。跨版本升级服务端时，首次启动会补充所需的数据表。仅更新 App 不会迁移服务端数据库。

只有从尚未使用独立账号的早期家庭共享口令版本升级时，原口令会迁移给相册主人，账号是 `owner`；旧的登录会失效。登录后建议修改成自己的新密码。

原家人记录不会被删除。管理员为某位原家人创建邀请时，选择对应记录；家人接受邀请后，旧照片仍会显示原上传人，并归到他的账号下面。不要为同一个家人重复建立不相关的记录。

如果需要回退旧版，应同时恢复升级前的代码和数据库备份，不要让旧代码直接写入升级后的数据库。

## 恢复验证

在一个单独目录或备用服务器恢复备份，先确认能登录，再抽查不同年份的照片、视频播放、手动修改的拍摄时间和家人权限。存在多位宝宝时，还要核对切换、不同家人的访问范围、共享照片各自的回收站与留言、成长代表照和故事册。已归档宝宝应保留资料，并且只有家庭管理员能恢复。使用云存储时，还要确认密钥能够解密、原文件能够读取。确认这些都正常后再替换正在使用的服务。
